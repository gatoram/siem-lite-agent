# SIEM-lite: AI-агент для аналізу логів безпеки

## Мета проєкту

Навчальний прототип, що демонструє принцип "agentic SOC": AI-агент бере на
себе аналітичну роботу, яку зазвичай виконує людина-аналітик вручну,
переглядаючи алерти в SIEM-системі. Система стежить за логами в реальному
часі, rule-based шар відсіює підозрілі події, AI-агент їх аналізує (з
можливістю самостійно перевірити репутацію IP через зовнішній API) і
сповіщає про критичні інциденти в Telegram.

Курсова робота, кібербезпека, 4 курс. Весь код пишеться через AI-агента для
кодування (Claude Code), а не вручну.

## Архітектура

```
[SSH / Web / Firewall логи] → [Парсер] → [Rule-based детектор] → [AI-агент + VirusTotal/AbuseIPDB tool use] → [Telegram-алерт + звіт] → [веб-дашборд]
```

Усі джерела логів (SSH auth.log, web access.log, firewall ufw/iptables)
парсяться в ОДНАКОВИЙ уніфікований формат — так rule-based детектор і агент
працюють з даними, не знаючи з якого джерела вони прийшли. Третє джерело
(firewall) так і додано: новий парсер, рядок у реєстрі парсерів `main.py` і
нове правило детектора, без переробки решти пайплайну.

### Уніфікований формат події

```json
{
  "timestamp": "2026-09-30T03:22:14",
  "source_ip": "203.0.113.4",
  "log_source": "ssh" | "web" | "firewall",
  "event_type": "login_fail" | "login_success" | "http_request" | "firewall_block" | ...,
  "raw": "оригінальний рядок логу",
  "meta": { "user": "root", "path": "/admin", "status_code": 401, ... }
}
```

`meta` залежить від джерела: ssh — user, auth_method, port; web — path,
query, status_code, user_agent; firewall — proto, dpt (порт призначення),
spt, interface, dst, action (префікс LOG-правила, напр. `UFW BLOCK`).

## Компоненти

1. **Генератор тестових логів** (`generate_logs.py`) — синтетичний
   `auth.log` (SSH), `access.log` (nginx-формат) і `firewall.log` (ufw) з
   вкрапленими атаками: brute-force, сканування шляхів, SQLi/XSS-спроби,
   сканування портів. Потрібен для розробки й демо без залежності від
   реальної інфраструктури. У `firewall.log`: ~200 блокувань інтернет-шуму
   (1-3 порти з IP), скан 25 портів з 198.51.100.200 за 3 хв до сканування
   шляхів з того ж IP (розвідка → атака), і два "майже скани", що не мають
   спрацьовувати: 12 портів по одному на годину і 40 спроб в один порт.

2. **Парсери** (`parsers/ssh_parser.py`, `parsers/web_parser.py`,
   `parsers/firewall_parser.py`) — перетворюють сирі рядки в уніфікований
   формат події (вище). Firewall-парсер розбирає рядки ядра (ціль LOG у
   netfilter) з ufw і iptables: префікс з ALLOW/ACCEPT → `firewall_allow`,
   AUDIT → пропускається, решта (`UFW BLOCK`, `IPTABLES-DROP`, без
   префікса) → `firewall_block`; далі пари KEY=VALUE (SRC, DST, PROTO, DPT…).
   SSH-парсер перевірено на реальному лозі (`real_logs/OpenSSH_2k.log`,
   вибірка OpenSSH з Loghub, logpai/loghub): розпізнаються всі рядки
   Failed/Accepted, включно з `message repeated N times: [...]` (одна подія з
   `meta.repeated = N`; детектор і історія рахують її як N спроб).

   Формат syslog-рядка (SSH і firewall) визначається автоматично по кожному
   рядку, без прапорців (спільний модуль `parsers/syslog_time.py`):
   - старий (RFC 3164, Loghub, синтетичні логи): `Sep 30 03:22:14 host sshd[PID]: ...`
     — року немає, береться з `--year` / параметра `year`, час місцевий;
   - Ubuntu 24.04+ (rsyslog за замовчуванням): `2026-11-04T20:58:02.245641+00:00
     host sshd-session[PID]: ...` — ISO 8601 з поясом, рік у рядку (`year`
     ігнорується), час переводиться в UTC (як у web), мікросекунди
     зберігаються. Процес `sshd-session` (OpenSSH 9.8+) приймається нарівні
     з `sshd` і пишеться в `meta.process`.

3. **Rule-based детектор** (`detector.py`) — правила на першому етапі:
   - brute-force: N невдалих логінів за M хвилин з одного IP (SSH); якщо
     після серії з того ж IP був успішний вхід — severity Critical
     (`details.login_success_after`, `compromised_user`)
   - path_scanning: багато різних шляхів за короткий час, більшість 403/404 (web)
   - port_scanning: `PORT_SCAN_MIN_PORTS` (10)+ різних портів призначення
     заблокованих пакетів з одного IP за `PORT_SCAN_WINDOW` (5 хв), severity
     Medium — розвідка перед атакою (firewall)
   - SQLi/XSS: ключові патерни в URL-параметрах (web)

   Правила лишаються зрозумілими й розширюваними — кожне нове правило це
   окрема функція, яка приймає список подій і повертає список інцидентів.

4. **AI-агент-аналітик** (`agent.py`) — приймає інцидент (+ історію IP з
   SQLite), викликає LLM. Оголошений tool `check_ip_reputation`
   (AbuseIPDB) — агент сам вирішує, коли його викликати. Повертає JSON: тип
   загрози, severity (Low/Medium/High/Critical), пояснення, рекомендацію.

   Правила severity (у системному промпті + перевірка в коді): поведінка з
   логів важливіша за репутацію; репутація може лише підвищити severity
   (нульовий score / зарезервована IP = "немає даних", а не "безпечно");
   severity не нижче за детектор — інакше код залишає оцінку детектора і
   пише `severity_note`; успішний вхід після brute-force = Critical; висновки
   лише з наданих даних, за їх відсутності — "даних немає".

   Аналітичний LLM — **Gemini API** (`google-genai`, безкоштовний тариф;
   модель у константі `GEMINI_MODEL`). Провайдер змінний: спільний
   інтерфейс `LLMProvider`, вибір через `LLM_PROVIDER` у `.env`; наступний
   кандидат — Ollama (локальна модель). Режим `--dry-run` працює без
   жодних API-викликів. Помилки 429/503 не валять програму — виклик
   повторюється з паузою.

   Запуск: `py -3 main.py batch sample_logs/auth.log sample_logs/access.log --ai`
   (`--dry-run` — без API, `--rule brute_force` — лише одне правило,
   `--max-ai N` — агент аналізує лише N найсерйозніших інцидентів: за
   severity детектора, потім за кількістю подій; через ліміт безкоштовного
   тарифу Gemini).

5. **Історія по IP** (`history.py`, SQLite `history.db`) — кожна подія по IP
   зберігається (без дублікатів при повторному прогоні), щоб агент бачив
   патерн поведінки за час, а не ізольовану подію. `ip_summary(ip)`: усього
   подій (і по джерелах), невдалі/успішні входи, заблоковані firewall-ом
   пакети (`firewall_blocks`), чи був успішний вхід після серії невдалих
   (`success_after_failures`), перша й остання поява. `main.py batch` пише
   всі події в базу і передає зведення агенту разом з інцидентом.

6. **Сповіщення** (`notifier.py`) — при severity High/Critical (поріг —
   константа `NOTIFY_MIN_SEVERITY`): повідомлення в Telegram через Bot API
   (`requests.post` на `sendMessage`). Коротке, для телефона: severity з
   емодзі, правило, IP, кількість подій, час, а далі висновок AI-агента
   (тип загрози, пояснення, рекомендація) або, якщо AI-аналізу не було, дані
   детектора. Дублікати не надсилаються: інцидент = (IP, правило, час першої
   події), надіслані записуються в таблицю `notifications` у `history.db`.
   Повторно той самий інцидент надсилається лише з вищою severity
   (ескалація в live-режимі). Недоступний Telegram — попередження, програма працює далі (інцидент
   спробує надіслатись наступного запуску).

   Запуск: `py -3 main.py batch sample_logs/*.log --ai --notify`
   (`--dry-run` — повідомлення друкуються в консоль; `--ip` — лише інциденти
   з цього IP). Всі інциденти (не лише критичні) пишуться у звіт/лог-файл —
   ще не реалізовано.

7. **Точка входу** (`main.py`) — режим "live" (файловий watcher/tail -f по
   логах, працює у фоні постійно) і режим "batch" (одноразовий прогін
   готового файлу — для тестування й демо).

   Batch (реалізовано): `py -3 main.py batch sample_logs/auth.log sample_logs/access.log sample_logs/firewall.log`.
   Формат кожного файлу (ssh / web / firewall) визначається автоматично за першими
   рядками; результат — таблиця інцидентів у консолі (`rich`) з кольором
   severity і підсумком.

   Live (реалізовано): `py -3 main.py live live_logs/auth.log live_logs/access.log --ai --notify`.
   Стежить за файлами як `tail -f` з кінця (опитування раз на `--poll` с;
   файл, якого ще немає, чекає; обрізання/ротацію переживає). Нові рядки →
   парсер → `history.db` → детектор по ковзному вікну останніх подій
   (`live.WINDOW` = 35 хв: серія brute-force + вікно успішного входу; межа
   рахується окремо для кожного джерела, бо в них різні часові пояси). Кожен новий
   інцидент (IP + правило + first_seen) AI-агент аналізує один раз, поки
   атака триває; повторно — лише при ескалації severity детектора
   (brute-force High → Critical після успішного входу), і тоді ж іде друге
   сповіщення. `--ai`, `--notify`, `--dry-run` як у batch; `--max-ai N` —
   ліміт AI-аналізів на сесію; `--duration` — автозупинка для тестів. У
   консолі рядок статусу і панель для кожного нового інциденту; Ctrl+C —
   зупинка з підсумком. Логіка без консолі — у `live.py`.

   Демо: `simulate_attack.py` дописує в `live_logs/` (у `.gitignore`)
   звичайний трафік з поточним часом (рядок раз на 1-2 с), через
   `--attack-after` с — brute-force з 203.0.113.99 з успішним входом admin,
   через `--sqli-after` с — SQLi з 192.0.2.150.

8. **Веб-дашборд** (`dashboard.py` + `dashboard.html`) — SOC-консоль у
   браузері: `py -3 dashboard.py` → http://127.0.0.1:8000 (слухає лише
   127.0.0.1; `--db` — інша база). Дашборд нічого не аналізує, а лише читає
   `history.db`: batch і live пишуть туди не тільки події, а й інциденти з
   висновками агента (таблиця `incidents`, `History.store_incident`; ключ
   rule + source_ip + first_seen). Повторний запис оновлює кількість подій і
   last_seen, severity не знижує, а висновок агента замінює лише новий
   висновок. Підсумкова `severity` — вища з детектора й агента. База у WAL,
   тож читання не блокує запис live.

   Flask віддає одну HTML-сторінку і JSON-ендпоінти (`/api/summary`,
   `/api/incidents` з фільтрами severity/rule/source, `/api/incidents/<id>`,
   `/api/timeline`, `/api/top_ips`); сторінка опитує їх кожні 3 с. На екрані:
   картки (подій, інцидентів, Critical/High/Medium), графік подій за часом
   надходження в базу (кошики по 10 с за 15 хв; час із самих логів не
   годиться, бо SSH місцевий, а web — UTC), топ-5 IP за кількістю
   інцидентів, таблиця інцидентів (найновіші зверху, колір і значок
   severity). Клік на рядок розкриває сирі рядки логу, ланцюжок tool calls
   агента з відповіддю AbuseIPDB, пояснення й рекомендацію.

   Безпека: логи пише атакуючий, тому дані з логів і від моделі виводяться
   лише як текст (`textContent`, без `innerHTML`). Content-Security-Policy
   дозволяє лише скрипт і стилі з nonce цієї відповіді, тож навіть пропущена
   HTML-вставка не виконає `<script>` чи `onerror=`. `test_dashboard.py`
   перевіряє це в headless Edge/Chrome (`--dump-dom`): payload
   `<script>alert(1)</script>` з access.log показано як текст.

## Стек

- Python 3.11+
- `google-genai` (Gemini API — аналітичний LLM агента)
- `pandas`
- `sqlite3` (стандартна бібліотека)
- `requests` (Telegram Bot API, AbuseIPDB)
- `python-dotenv` (ключі з `.env`, не в репозиторії)
- `rich` (форматований консольний вивід у `main.py`)
- `flask` (веб-дашборд, лише читає `history.db`)

Залежності фіксуються в `requirements.txt` у міру того, як починають
використовуватись у коді: `py -3 -m pip install -r requirements.txt`.

Ключі — у `.env` (шаблон: `.env.example`): `LLM_PROVIDER`, `GEMINI_API_KEY`,
`ABUSEIPDB_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`.

## Milestone-план

**Milestone 1:**
- Парсери SSH + web в уніфікованому форматі
- Rule-based детектор: brute-force, scanning, SQLi (2-3 правила мінімум)
- Перевірка на синтетичних логах із симульованими атаками

**Milestone 2:**
- AI-агент з tool use до AbuseIPDB
- SQLite-історія по IP
- Telegram-сповіщення для критичних подій
- Демо: повний ланцюжок від сирого логу до алерту в Telegram

**Після Milestone 2:**
- Третє джерело логів: firewall (ufw/iptables), правило port_scanning
- Веб-дашборд (SOC-консоль) поверх `history.db`

## Що НЕ входить у скоуп (щоб не розпорошуватись)

- Реальна production-інфраструктура — тільки синтетичні/тестові логи
- ML-модель для детекції аномалій — лишається rule-based (можна згадати як
  напрямок розвитку в кінці презентації)
- Аутентифікація й доступ до дашборду ззовні — він слухає лише 127.0.0.1

## Перший крок

Створити `generate_logs.py`, що генерує:
- `sample_logs/auth.log` — ~200 нормальних SSH-логінів + 1 вкраплена
  brute-force атака (30 failed спроб за 2 хвилини з одного IP) + друга
  brute-force з іншого IP (25 failed), після якої вхід admin успішний
- `sample_logs/access.log` — ~200 нормальних web-запитів + 1 вкраплена
  спроба сканування шляхів + 1 SQLi-спроба в параметрі запиту
